(The Big Picture)} % ============================================================= \begin{definitionbox}[Definition --- Live Forensics] \textbf{Live forensics} is the process of collecting digital evidence from a computer (or other device) \emph{while it is still turned on and running}. \medskip \textbf{Think of it like this:} Imagine police arrive at a crime scene and the suspect's laptop is open on the desk, programs running, websites visible. Live forensics means carefully gathering information from that running laptop \emph{before} you power it off. \end{definitionbox} \subsection{Live vs.\ Dead/Static Forensics} \begin{center} \renewcommand{\arraystretch}{1.5} \begin{tabular}{>{\bfseries}p{4cm} p{5.5cm} p{5.5cm}} \toprule \rowcolor{lightblue} \textbf{Feature} & \textbf{Live Forensics} & \textbf{Dead / Static Forensics} \\ \midrule System state & Computer is \textcolor{defgreen}{\textbf{ON}} and running & Computer is \textcolor{warnred}{\textbf{OFF}}; work from a disk image \\ Data type & \textbf{Volatile} data (RAM, running programs, open network connections) & \textbf{Non-volatile} data (files saved on the hard drive) \\ Risk & You might accidentally \emph{change} something on the running system & Evidence is ``frozen'' --- less risk of change \\ Unique advantage & Can capture passwords, encryption keys, chat sessions, live network traffic & Can search entire disk without time pressure \\ Real-world analogy & Photographing a whiteboard before someone erases it & Reading a printed letter after the meeting is over \\ \bottomrule \end{tabular} \end{center} \begin{examtip} The exam loves asking you to \emph{compare} live and dead forensics. Memorise the table above --- especially the ``volatile vs.\ non-volatile'' distinction. \end{examtip} % ============================================================= \section{Why Do We Need Live Forensics?} % ============================================================= There are two sides: \textbf{Need} (we have no choice) and \textbf{Opportunity} (it gives us extra evidence). \subsection{The Need} \begin{enumerate}[label=\arabic*., leftmargin=*] \item \textbf{Huge storage disks.} Modern servers have terabytes of data. Copying (``mirroring'') an entire 4\,TB disk takes many hours. You may not have that time. \item \textbf{Mission-critical systems.} Suppose the suspect's computer is a hospital server running life-support monitoring. You cannot just pull the plug --- people could die. You \emph{must} collect evidence while it runs. \item \textbf{Court orders are limited.} A warrant might only let you look at \emph{one} specific server out of 30. You need a quick, live check to justify a broader warrant. \end{enumerate} \subsection{The Opportunity} \begin{enumerate}[label=\arabic*., leftmargin=*] \item \textbf{Speed.} A quick live scan can be done in minutes --- no need to haul away hardware. \item \textbf{Exclusive data.} Some evidence \emph{only} exists in RAM (temporary memory). Once you power off, it is \textbf{gone forever}. Examples: \begin{itemize} \item Passwords typed into a web browser \item Encryption keys protecting a locked hard drive \item Chat messages that were never saved to disk \end{itemize} \item \textbf{Context.} Seeing what is running \emph{right now} helps you decide which parts of the hard drive to focus on later during static analysis. \end{enumerate} \begin{examplebox}{Why RAM matters} Imagine a suspect is logged into their online banking with a password manager. The password exists in the computer's RAM right now. If you turn the computer off first, the password disappears from RAM and you must crack the encrypted password file instead --- which could take weeks or be impossible. \end{examplebox} % ============================================================= \section{Live Forensics Goals} % ============================================================= When you perform live forensics, you are trying to answer these questions: \begin{center} \renewcommand{\arraystretch}{1.4} \begin{tabular}{>{\bfseries\color{examblue}}l p{10cm}} \toprule \rowcolor{lightblue} \textbf{Goal} & \textbf{Plain-English Explanation} \\ \midrule What is happening now? & Which programs are running? A password you type may get \textbf{duplicated dozens of times} across different memory buffers. \item Even though data is often encrypted \emph{on disk}, it is usually \textbf{not encrypted in RAM} (otherwise the CPU could not process it). \item Places a password might sit in RAM: \begin{itemize} \item Kernel buffers (the operating system's internal storage) \item Window manager memory (the part that draws your screen) \item Application buffers (the browser's own storage) \item Dynamic memory allocator (general-purpose memory pool) \end{itemize} \end{itemize} \begin{examplebox}{The Password Duplication Problem} You type your email password into Firefox. Here is what happens in RAM: \begin{enumerate} \item The keyboard driver stores each keystroke $\rightarrow$ \textbf{copy 1} \item The window manager passes it to Firefox $\rightarrow$ \textbf{copy 2} \item Firefox stores it in a text field buffer $\rightarrow$ \textbf{copy 3} \item Firefox sends it to the network module $\rightarrow$ \textbf{copy 4} \item The OS kernel buffers the network packet $\rightarrow$ \textbf{copy 5} \end{enumerate} That is at least 5 copies of your password floating around in RAM, even though you only typed it once. \end{examplebox} \subsection{Persistence of Memory (Post-Reboot)} \begin{itemize} \item Some systems \emph{retain} data in RAM even after a reboot (warm reboot or even sometimes a cold reboot). \item This depends on the hardware model and BIOS settings. \item This can be used as a ``last resort'' to recover live data if the computer was recently switched off. \item This is an active research area in \textbf{memory forensics}. \end{itemize} \begin{examtip} Be ready to explain that RAM data can sometimes survive a reboot, making memory forensics possible even after shutdown. \end{examtip} % ============================================================= \section{Constraints \& Rules of Live Forensics} % ============================================================= \subsection{Key Constraints} \begin{center} \renewcommand{\arraystretch}{1.4} \begin{tabular}{>{\bfseries\color{warnred}}c p{11cm}} \toprule \rowcolor{lightred} \textbf{\#} & \textbf{Constraint} \\ \midrule 1 & \textbf{You need physical or remote access} to the running system (even if only for a short time). \\ 2 & \textbf{Minimise changes.} Everything you do on the system (inserting a USB, running a tool) \emph{changes} something. You must keep changes as small as possible. \textbf{Remember ACPO Principle 1:} no action should change data which may be relied upon in court. \\ 3 & \textbf{Minimise impact} on the system, especially if it is mission-critical (e.g.\ a hospital server). \\ 4 & \textbf{Record every step.} Write down every command you run and every USB you plug in. If you leave ``fingerprints,'' you must be able to explain them in court. \\ \bottomrule \end{tabular} \end{center} \begin{examplebox}{The Detective's Fingerprints} Think of a real crime scene. A detective picks up a ransom note with bare hands and leaves fingerprints on it. Now the defence lawyer asks: ``How do we know those aren't the criminal's fingerprints?'' The same thing happens in digital forensics. If you run a program on the suspect's computer, you leave traces (file dates change, memory shifts). You \emph{must} document exactly what you did so no one can argue you planted evidence. \end{examplebox} \subsection{Minimising Your Footprint} \begin{itemize}[leftmargin=*] \item Use \textbf{trusted, pre-compiled tools} --- ideally carry them on a read-only USB so you do not install anything on the suspect's machine. \item Keep a \textbf{low profile} --- especially if the suspect might be monitoring the system (you do not want to tip them off). \item Any artifacts (changes) you create \textbf{can be explained in court} if properly documented. \end{itemize} % ============================================================= \section{Dangers of Live Forensics --- Rootkits} % ============================================================= \begin{definitionbox}[Definition --- Rootkit] A \textbf{rootkit} is a type of malware that hides itself (and other malware) from the operating system and from forensic tools. It is like an invisible burglar who also makes the security cameras show a fake ``all clear'' feed. \end{definitionbox} \subsection{Two Types of Rootkits} \begin{center} \renewcommand{\arraystretch}{1.5} \begin{tabular}{>{\bfseries}p{3.5cm} p{5.5cm} p{5.5cm}} \toprule \rowcolor{lightblue} & \textbf{User-Mode Rootkit} & \textbf{Kernel-Mode Rootkit} \\ \midrule Difficulty & Shallow trickery (easier to make) & Deep trickery (very advanced) \\ How it works & Replaces normal commands like \texttt{ls} (list files), \texttt{ps} (list processes), \texttt{du}/\texttt{df} (disk usage) with fake versions that hide the malware & Modifies the \textbf{OS kernel itself} (the core brain of the operating system) to produce fake results \\ What it hides & Changes disk space statistics, hides processes from the process list & Can hide files, blocks of memory, entire programs --- even if you bring your own trusted tools \\ Defence & Bring your own trusted copies of \texttt{ls}, \texttt{ps}, etc.\ on a USB & Very hard to detect; even trusted tools can be fooled because the OS kernel is compromised \\ \bottomrule \end{tabular} \end{center} \subsection{How Kernel-Mode Rootkits Fool Everything} \begin{itemize} \item \textbf{Disk drivers:} The rootkit intercepts all disk reads, so it can hide files at the hardware level. \item \textbf{Virtual memory system:} It hacks the memory management, hiding malicious processes. \item \textbf{Shared libraries (DLLs):} It replaces shared code libraries. Even your ``trusted'' executable uses DLLs from the OS --- if those are replaced, your trusted tool is compromised. \item The \emph{only} true defence is to use \textbf{statically linked executables} (programs that contain all their code inside themselves and do not rely on the OS for shared libraries). \end{itemize} \begin{warningbox}{Exam Favourite} The exam may ask: ``Why might your trusted forensic tools still give wrong results on a live system?'' Answer: \textbf{Kernel-mode rootkits} modify the OS itself. Even a clean copy of \texttt{ls} or \texttt{ps} relies on the OS kernel to read files and processes. If the kernel is compromised, it feeds lies to every tool. The only protection is statically linked binaries. \end{warningbox} % ============================================================= \section{Approach to Live Forensics} % ============================================================= \subsection{Evidence Acquisition Scenarios} \begin{center} \renewcommand{\arraystretch}{1.4} \begin{tabular}{>{\bfseries\color{examblue}}p{3.5cm} p{11cm}} \toprule \rowcolor{lightblue} \textbf{Scenario} & \textbf{What You Do} \\ \midrule Triage & You have \emph{limited time}. The lecture identifies several specific analysis questions: \begin{center} \renewcommand{\arraystretch}{1.4} \begin{tabular}{>{\bfseries\color{examblue}}p{4cm} p{10.5cm}} \toprule \rowcolor{lightblue} \textbf{Analysis Question} & \textbf{What You Are Looking For} \\ \midrule Are things ``not right''? & Are processes or files \textbf{hidden}? The lecture (and Lecture Topic 3) explains that each \textbf{process} (running application) gets its own block of memory, divided into \textbf{segments}: \begin{center} \renewcommand{\arraystretch}{1.5} \begin{tabular}{>{\bfseries\color{examblue}}p{2.5cm} p{6cm} p{5.5cm}} \toprule \rowcolor{lightblue} \textbf{Segment} & \textbf{What It Stores} & \textbf{Real-World Analogy} \\ \midrule Text & The \textbf{machine code} of the compiled program --- the actual CPU instructions. This segment is usually \emph{read-only}. & The printed recipe in a cookbook --- you read it but don't write on it. \\ \midrule Stack & Manages the \textbf{function/method call structure} during execution. Every time a function is called, a new ``frame'' is pushed onto the stack; when it returns, the frame is popped off. Local variables live here. & A stack of sticky notes --- you add one on top each time you start a sub-task, and remove it when you finish. \\ \midrule Heap & Contains \textbf{dynamically allocated memory} --- memory that the program explicitly requests at runtime (e.g.\ when you create a new object or variable). algorithm that takes \emph{any} input (a file, a password, a disk image) and produces a \textbf{fixed-length string} (the ``hash'' or ``digest''). Even a \textbf{tiny change} in the input produces a \textbf{completely different} hash. \medskip \textbf{Three key properties:} \begin{enumerate}[nosep] \item \textbf{Deterministic:} Same input $\rightarrow$ same hash, every time. \item \textbf{One-way:} You cannot reverse the hash to get the original data. \item \textbf{Avalanche effect:} A single-bit change in the input produces a completely different hash output. \end{enumerate} \medskip Think of a hash as a \textbf{unique digital fingerprint} for a file. The lab walks through the standard steps used on a real compromised running system, following the \textbf{order of volatility}: \begin{enumerate}[nosep] \item Most volatile first: contents of RAM, running processes \item Less volatile next: data stored on disk (offline analysis) \end{enumerate} \end{definitionbox} \subsubsection{Static vs.\ Dynamic Linking --- Why It Matters} \begin{center} \renewcommand{\arraystretch}{1.4} \begin{tabular}{>{\bfseries\color{examblue}}p{3.5cm} p{5cm} p{5.5cm}} \toprule \rowcolor{lightblue} & \textbf{Dynamically Linked} & \textbf{Statically Linked} \\ \midrule What it means & Program loads shared libraries (\texttt{.so} on Linux, \texttt{.dll} on Windows) at runtime & Program contains \textbf{all} library code built into the executable itself \\ \midrule Risk in forensics & Shared libraries may have been \textbf{tampered with} by an attacker; running the program also \textbf{updates access times} on those library files & Much safer because the program does not depend on any files on the compromised system \\ \midrule Check with & \texttt{ldd /bin/ls} $\rightarrow$ lists external libraries & \texttt{ldd static/ls} $\rightarrow$ ``not a dynamic executable'' \\ \bottomrule \end{tabular} \end{center} \begin{examtip} If the exam asks ``Why should forensic investigators use statically linked binaries?'' the answer is: \textbf{dynamically linked programs rely on shared libraries that may have been tampered with by an attacker.} Statically compiled programs carry all their code internally, so they cannot be fooled by modified libraries. After collecting live evidence, you may want to \textbf{force power off} (``pull the plug'') rather than performing a normal shutdown. Why? \begin{itemize}[nosep] \item A normal shutdown (\texttt{halt}/\texttt{shutdown}) runs scripts that may \textbf{destroy evidence} --- malware often includes cleanup routines that trigger on shutdown. \item The \texttt{sync} command flushes file system buffers to disk before power-off: \end{itemize} \texttt{sync; sync} (run twice for safety, then force power off) \end{warningbox} \begin{examtip} If the exam asks ``Why might an investigator force a power-off instead of a normal shutdown?'' the answer is: a normal shutdown runs scripts that may \textbf{delete evidence or trigger malware cleanup routines}. Force power-off preserves the disk in its current state. Always run \texttt{sync} first to flush pending writes. \end{examtip} % ============================================================= \section{Complete Process Summary Flowchart} % ============================================================= \begin{center} \begin{tikzpicture}[ node distance=1.2cm, box/.style={rectangle, draw=examblue, fill=lightblue, text width=10cm, minimum height=1cm, align=center, font=\small}, arrow/.style={->, thick, examblue} ] \node[box] (step1) {\textbf{Step 1:} Arrive at scene --- computer is ON}; \node[box, below of=step1] (step2) {\textbf{Step 2:} Document everything (photograph screen, note programs running)}; \node[box, below of=step2] (step3) {\textbf{Step 3:} Collect volatile data FIRST (RAM dump, network connections, running processes)}; \node[box, below of=step3] (step4) {\textbf{Step 4:} Check for encryption --- capture keys from RAM before shutdown}; \node[box, below of=step4] (step5) {\textbf{Step 5:} Live disk imaging (if time/storage permits)}; \node[box, below of=step5] (step6) {\textbf{Step 6:} Live file carving for deleted evidence}; \node[box, below of=step6] (step7) {\textbf{Step 7:} Power off and perform static/dead forensics on the disk image}; \draw[arrow] (step1) -- (step2); \draw[arrow] (step2) -- (step3); \draw[arrow] (step3) -- (step4); \draw[arrow] (step4) -- (step5); \draw[arrow] (step5) -- (step6); \draw[arrow] (step6) -- (step7); \end{tikzpicture} \end{center} % ============================================================= \section{Quick-Reference Exam Cheat Sheet} % ============================================================= \begin{center} \renewcommand{\arraystretch}{1.5} \begin{tabular}{>{\bfseries\color{examblue}}p{4.5cm} p{10cm}} \toprule \rowcolor{lightblue} \textbf{Exam Question} & \textbf{Key Points to Include} \\ \midrule What is live forensics?
