Yes. Use this exact route.

The path most likely to work in Debian is the **official non-snap install**, not the snap. Autopsy’s own Linux instructions say there are two paths on Linux: snap, or the standard Debian-based flow of installing prerequisites, then The Sleuth Kit, then Autopsy itself. The download page for 4.22.1 also says Linux needs the **Autopsy ZIP** plus the **Sleuth Kit Java `.deb`**. For 4.22.1 specifically, the release notes say it uses **Sleuth Kit 4.14.0**, and the release notes also warn that the original ZIP link was wrong and that the **`_v2.zip`** is the correct ZIP. ([GitHub][1])

Before you start, set the VM to a sane config: keep RAM around **6–8 GB**, give it **2 or 4 CPU cores**, and make sure the Debian VM has **plenty of free disk** for the Autopsy case data and indexing. That part is practical advice from experience, not an Autopsy requirement.

## Route A: get it working properly in Debian

### 1. Fix the shared folder first

VirtualBox shared folders require **Guest Additions** in the guest, and Linux guests mount them with the `vboxsf` filesystem. Oracle’s docs give the Linux mount syntax as `mount -t vboxsf sharename mountpoint`, and they also show the `/etc/fstab` format if you want it to mount automatically. They note that `uid`, `gid`, and `mode` options are useful so normal users can access the share. ([Oracle Docs][2])

On the **host**, make sure the shared folder exists in the VM settings:

* Shared Folders → add your host evidence folder
* Share name: `DF_Shared`
* Make it permanent

Then boot Debian and run:

```bash
sudo apt update
sudo apt install virtualbox-guest-utils virtualbox-guest-x11 -y
sudo reboot
```

After reboot:

```bash
sudo mkdir -p /mnt/shared
sudo mount -t vboxsf -o uid=$(id -u),gid=$(id -g),mode=0775 DF_Shared /mnt/shared
ls -lh /mnt/shared
ls -lh /mnt/shared/lubuntu_forensic.dd
```

If that last command does **not** show the `.dd` file, stop. Autopsy is not the problem yet. Your shared folder is still broken.

If you want it mounted automatically every boot:

```bash
echo 'DF_Shared /mnt/shared vboxsf defaults,uid=1000,gid=1000,mode=0775 0 0' | sudo tee -a /etc/fstab
sudo mount -a
```

Use `1000` only if your normal user is UID 1000. Check with:

```bash
id
```

### 2. Download the correct Autopsy files

For Linux, you need:

* the **Autopsy ZIP**
* the **Sleuth Kit Java `.deb`**

For version **4.22.1**, use:

* `autopsy-4.22.1_v2.zip`
* `sleuthkit-java_4.14.0-1_amd64.deb`

That pairing matters because Autopsy 4.22.1 uses Sleuth Kit 4.14.0, and the project explicitly says the `_v2.zip` is the correct ZIP for that release. ([Autopsy][3])

Put both files in `~/Downloads`.

### 3. Install Java and prerequisites

Autopsy’s Linux instructions say to run `install_prereqs_ubuntu.sh`, and they note that the script outputs the path to the **Java 17** installation. The same document says the install command for Autopsy needs the Java 17 home path. ([GitHub][1])

Run:

```bash
sudo apt update
sudo apt install default-jdk unzip wget -y
java -version
```

Then unzip the Autopsy package:

```bash
cd ~/Downloads
unzip autopsy-4.22.1_v2.zip -d autopsy-src
cd autopsy-src/autopsy-4.22.1
chmod u+x linux_macos_install_scripts/*.sh
./linux_macos_install_scripts/install_prereqs_ubuntu.sh
```

Now find your Java 17 path:

```bash
update-java-alternatives -l | grep 17
```

You want something like:

```bash
/usr/lib/jvm/java-17-openjdk-amd64
```

### 4. Install Sleuth Kit Java

Autopsy’s Linux instructions say to install the Sleuth Kit `.deb` directly with `apt install /path/to/...deb`. ([GitHub][1])

Run:

```bash
cd ~/Downloads
sudo apt install ./sleuthkit-java_4.14.0-1_amd64.deb
```

### 5. Install Autopsy itself

Autopsy’s Linux instructions say to run `install_application.sh` with the ZIP path, install directory, and Java home. They also recommend `--nosplash` later because the first-run window can hide behind the splash screen. ([GitHub][1])

Run:

```bash
cd ~/Downloads/autopsy-src/autopsy-4.22.1
./linux_macos_install_scripts/install_application.sh \
  -z ~/Downloads/autopsy-4.22.1_v2.zip \
  -i ~/autopsy \
  -j /usr/lib/jvm/java-17-openjdk-amd64
```

If your Java path is different, use the one from `update-java-alternatives -l`.

### 6. Launch Autopsy

Use `--nosplash` on first launch. The official docs say Autopsy can look stalled because a window may appear behind the splash screen. ([GitHub][1])

Run:

```bash
~/autopsy/bin/autopsy --nosplash
```

### 7. Add the `.dd` image

In Autopsy:

* Create case
* Add Data Source
* Choose disk image / VM file
* Browse to `/mnt/shared/lubuntu_forensic.dd`

Use the **real file path**, not a symlink, for the first test.

If it loads, create the case on the Debian VM’s local disk, not inside the shared folder.

## If it still fails

Autopsy’s Linux docs say:

* if you see JavaFX errors, Java is wrong
* if you see reflective-access warnings or similar, the wrong Java may be in use
* `messages.log` is the place to check the Java version
* Autopsy first checks `jdkhome` in `etc/autopsy.conf`, then `$JAVA_HOME` if `jdkhome` is not set. ([GitHub][1])

So check this:

```bash
grep -n 'jdkhome' ~/autopsy/etc/autopsy.conf
echo $JAVA_HOME
```

If `jdkhome` is missing or wrong, set it:

```bash
sed -i 's|^#\?jdkhome=.*|jdkhome=/usr/lib/jvm/java-17-openjdk-amd64|' ~/autopsy/etc/autopsy.conf
```

Then relaunch:

```bash
~/autopsy/bin/autopsy --nosplash
```

If you get the JNI / `libtsk_jni` error again, that almost always means your Autopsy ZIP and Sleuth Kit Java `.deb` do **not** match. For 4.22.1, the correct pairing is the `_v2.zip` plus Sleuth Kit **4.14.0**. ([GitHub][4])

## Important Linux caveat

Autopsy’s own Linux/macOS notes say **not all current features are functional on Linux**, and they explicitly list **Recent Activity** among the known limitations. So if the app runs but that module is incomplete or flaky on Debian, that is not you being stupid; it is a documented limitation. ([GitHub][1])

## Route B: snap only if you insist

Autopsy’s snap exists, but the project’s snap config says it is a **strictly confined** snap and relies on interfaces like `block-devices`, `removable-media`, `mount-observe`, `fuse-support`, and `system-files-dev` to ingest data sources. That is why the snap route is more fragile. ([GitHub][5])

If you want to try it anyway:

```bash
sudo snap install autopsy
sudo snap connect autopsy:home
sudo snap connect autopsy:removable-media
sudo snap connect autopsy:mount-observe
sudo snap connect autopsy:fuse-support
sudo snap connect autopsy:system-files-dev
snap connections autopsy
autopsy --nosplash
```

Then point Autopsy at:

```bash
/mnt/shared/lubuntu_forensic.dd
```

If the snap still refuses to ingest, stop wasting time on the snap and use Route A.
