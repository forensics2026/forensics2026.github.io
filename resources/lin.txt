Good. The problem is simpler than you think.

Your command failed **before** Autopsy even entered the picture. The share did **not** mount, so `/mnt/shared/lubuntu_forensic.dd` does not exist yet. VirtualBox’s documented Linux syntax is just `mount -t vboxsf [-o OPTIONS] sharename mountpoint`, and auto-mounted Linux shares normally appear under `/media/sf_<sharename>`. Oracle also notes that access to auto-mounted shares in Linux is restricted to members of the `vboxsf` group. ([Oracle Docs][1])

The immediate fix is: **stop using `mode=0775` for now**. Your guest is rejecting that option, so use the simplest working mount first.

Run these commands exactly, in order:

```bash
sudo apt update
sudo apt install virtualbox-guest-utils virtualbox-guest-x11 -y
sudo usermod -aG vboxsf $USER
reboot
```

After reboot, first check whether VirtualBox already auto-mounted the share:

```bash
ls -lh /media
ls -lh /media/sf_DF_Shared
ls -lh /media/sf_DF_Shared/lubuntu_forensic.dd
```

If that works, you are done with the share. Use `/media/sf_DF_Shared/lubuntu_forensic.dd` in Autopsy. Auto-mounted Linux shares under `/media/sf_<name>` and `vboxsf` group access are the documented VirtualBox behavior. ([Oracle Docs][1])

If `/media/sf_DF_Shared` does **not** exist, do a manual mount with no `mode` option:

```bash
sudo mkdir -p /mnt/shared
sudo mount -t vboxsf DF_Shared /mnt/shared
ls -lh /mnt/shared
ls -lh /mnt/shared/lubuntu_forensic.dd
```

If that mounts but permissions are annoying, retry with only `uid` and `gid`:

```bash
sudo umount /mnt/shared 2>/dev/null
sudo mount -t vboxsf -o uid=$(id -u),gid=$(id -g) DF_Shared /mnt/shared
ls -lh /mnt/shared
ls -lh /mnt/shared/lubuntu_forensic.dd
```

Oracle’s manual explicitly documents `uid` and `gid` as useful mount options for letting normal users read and write shared folders; your screenshot shows the share name is being recognized, but your guest does not like the `mode` option as passed. ([Oracle Docs][1])

If manual mount still fails, check whether Guest Additions are actually active:

```bash
mount | grep vboxsf
groups
sudo dmesg | tail -50
```

What you want to see:

* your user is in `vboxsf`
* `vboxsf` appears in mounted filesystems
* `lubuntu_forensic.dd` is visible from either `/media/sf_DF_Shared/` or `/mnt/shared/`

Only **after that** should you try Autopsy.

For Autopsy on Debian, use the **official non-snap route**, not the snap. Autopsy’s Linux instructions say the Debian-based install is: install prerequisites, install the Sleuth Kit `.deb`, then install Autopsy from the ZIP. The 4.22.1 release notes also say that version uses **Sleuth Kit 4.14.0**, and that the correct ZIP is the **`_v2.zip`** build. ([GitHub][2])

Once the share is working, the install sequence is:

```bash
sudo apt update
sudo apt install default-jdk unzip wget -y
java -version
```

Then from your Downloads folder, using the correct files:

* `autopsy-4.22.1_v2.zip`
* `sleuthkit-java_4.14.0-1_amd64.deb`

Install them like this:

```bash
cd ~/Downloads
sudo apt install ./sleuthkit-java_4.14.0-1_amd64.deb
unzip autopsy-4.22.1_v2.zip -d autopsy-src
```

That is the installation flow Autopsy documents for Debian-based Linux, and the docs say the prerequisites script tells you the Java 17 path to use. ([GitHub][2])
